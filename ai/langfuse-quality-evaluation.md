# AI 기능을 평가하고 프롬프트를 함께 관리하기: Langfuse 도입 기록

설문을 검색하고, 만들고, 수정하고, 분석하는 과정에 AI를 연결했습니다. 기능이 늘자 결과의 품질을 어떻게 확인할지, PM도 프롬프트를 직접 고칠 수 있게 할지, 수정한 내용을 언제 운영에 반영할지 정해야 했습니다. 저는 Langfuse를 도입해 각 기능을 개발하는 부서가 실행 기록을 확인하고, 평가를 돌리고, 프롬프트를 관리할 수 있는 공통 환경을 만들었습니다.

도입의 출발점은 LLM의 결과를 설명하기 어렵다는 문제였습니다. 입력과 최종 출력만으로는 어느 단계에서 문제가 생겼는지 알기 어려웠습니다. 우선 실행 과정을 기록하고, 모델이나 프롬프트를 바꿨을 때 품질을 확인하자는 목표를 세웠습니다.

## PM도 프롬프트를 수정할 수 있도록 했습니다

처음에는 엔지니어가 코드에서 프롬프트를 관리했습니다. 관리할 프롬프트가 늘면서 PM도 내용을 직접 조회하고 수정할 수 있어야 했습니다. 그래서 사내 구성원이 초대를 통해 Langfuse에 접근하고, PM도 프롬프트를 수정할 수 있는 운영 방식을 만들었습니다.

수정 중인 프롬프트와 운영에 쓰는 프롬프트는 태그로 구분했습니다. 개발·QA 환경에서는 `latest` 프롬프트를, 운영 환경에서는 `production` 프롬프트를 조회하도록 했습니다. 운영에 반영하기 전에는 각 기능의 평가 점수를 확인하고 QA를 거쳤습니다.

코드와 프롬프트의 변경 이력은 Git에 모아 관리하고 싶었습니다. 프롬프트만 Langfuse에 남으면 변경을 확인할 곳이 늘어나기 때문입니다. 그래서 Langfuse의 Automation을 설정해 프롬프트를 `production`으로 승격하면 Git 반영용 PR이 자동으로 생성되도록 했습니다. PM은 Langfuse에서 프롬프트를 수정하고, 변경 내용은 Git에도 반영할 수 있도록 연결했습니다.

## 실행 기록에 평가 결과를 연결했습니다

AI 요청 하나에도 프롬프트, 모델 응답, 검색과 도구 실행이 얽힙니다. Langfuse로 이 흐름을 기록해 서비스가 모델에 무엇을 보냈고, 어떤 응답을 받아 다음 작업을 실행했는지 확인할 수 있게 했습니다. 모델 내부의 사고 과정을 볼 수 있는 것은 아니지만, 서비스의 실행 과정은 따라갈 수 있었습니다.

정상적으로 실행됐어도 사용자가 원한 결과인지는 따로 판단해야 했습니다. 그래서 등록된 평가 입력으로 기능을 실행하고, 결과를 평가해 점수로 남기도록 했습니다. 평가 점수는 실행 기록에 연결해 해당 요청의 처리 과정과 함께 확인할 수 있도록 했습니다.

평가 질문과 정답은 각 기능을 개발하는 부서에서 관리했습니다. 저는 이 평가들이 동작할 환경을 만드는 일을 맡았고, 일부 평가 작업에도 참여했습니다. 현재는 여러 부서가 이 환경에 프롬프트와 평가를 등록해 사용하고 있습니다.

## 평가의 우선순위는 의도 분류에 뒀습니다

초기에 가장 중요하게 본 평가 대상은 **의도 분류**였습니다. 사용자의 채팅 요청을 읽고 어떤 기능을 실행할지 결정하는 단계입니다. 분류 결과에 따라 호출할 MCP 도구가 달라지므로, 여기서 틀리면 뒤의 작업도 요청에서 벗어날 수 있었습니다. 이 때문에 의도 분류를 우선해서 평가했습니다.

예를 들어 “작년 리서치 보고서를 찾아줘”라는 요청에는 검색 의도를 정답으로 둘 수 있습니다. 이처럼 정답이 있는 항목은 같은 프롬프트와 요청으로 실행했을 때 정답이 재현되는지 확인했습니다. 분류 결과가 정답과 일치하는지를 점수로 기록했습니다.

## 설문 생성은 정답 대신 기준으로 평가했습니다

정답을 하나로 정하기 어려운 기능에서는 사용자의 요청과 결과를 LLM에 전달해 평가하는 LLM-as-a-Judge 방식을 주로 사용했습니다. 가장 많이 활용한 기능은 설문 생성이었습니다.

예를 들어 같은 대상을 두고 ‘주 이용 브랜드’와 ‘가장 자주 먹는 브랜드’를 각각 물으면, 문장은 달라도 수집하려는 정보가 겹칠 수 있습니다. 생성된 설문이 이런 문제를 포함하는지 다음 기준으로 평가했습니다. 이 서비스의 설문 생성에 적용한 기준입니다.

| 기준 | 확인한 내용 |
| --- | --- |
| 중복 질문 | 표현이 달라도 같은 정보를 묻는 문항이 있는지 |
| 보기의 일관성 | 같은 대상을 다루는 보기의 명칭·순서·개수가 일치하는지. 이전 응답을 가져와야 할 자리에 고정된 보기가 들어가지는 않았는지 |
| 응답 유도 방지 | 떠오르는 브랜드를 묻기 전에 브랜드명이 노출되지는 않는지. 질문에 답을 유도하는 예시나 표현이 있는지 |
| 문항 구조 | 표 형태 대신 개별 문항으로 나뉘어 있는지. 넓은 범위에서 구체적인 내용으로 질문이 이어지는지 |
| 응답자가 이해하기 쉬운 표현 | ‘취식’ 대신 ‘먹다’처럼 쉬운 말을 쓰는지. 참여 대상을 가리는 질문에서 탈락 조건이 드러나지는 않는지 |

평가 결과는 0~1 사이의 점수로 기록했습니다. 로직이나 프롬프트를 바꿀 때 이 점수로 품질이 유지되는지 판단했습니다. 운영 환경에서도 평가를 계속 실행하고 있으며, 비용을 고려해 운영 결과 중 약 5%를 샘플링해 평가하고 있습니다.

## 모델을 급히 교체할 때 기존 평가를 활용했습니다

사용하던 모델의 서비스가 중단되어 빠르게 다른 모델로 바꿔야 했던 적이 있습니다. 이때 미리 설정해 둔 평가를 활용했습니다. 교체할 모델로 기존 평가를 실행해, 평가 대상 항목에서 품질이 낮아지지 않았음을 확인한 뒤 모델을 교체했습니다.

## 평가 기준은 계속 살펴봐야 합니다

모델 교체 때 확인한 것은 등록된 평가에서의 품질이었습니다. 평가에 포함되지 않은 요청까지 같은 결과를 보장하지는 않습니다. 평가 사례가 실제 요청을 충분히 담고 있는지, LLM이 매긴 점수는 어떤 기준에 따른 것인지 계속 살펴봐야 합니다.

이번 작업에서는 각 부서가 평가 내용을 관리하고, PM이 프롬프트를 수정하며, 변경 후 품질을 확인할 수 있는 환경을 만들었습니다. 제가 만든 환경 위에서 여러 기능의 평가가 돌아가고, 실제 모델 교체에도 그 평가가 활용됐습니다.

설문 검색 자체의 품질을 어떻게 측정했는지는 [OpenSearch 검색 품질 개선 기록](../search/opensearch-search-quality.md)에 따로 정리했습니다.
